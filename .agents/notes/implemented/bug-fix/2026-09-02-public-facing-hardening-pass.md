# Agent Note: public-facing-hardening-pass

Status: implemented

## Problem

The user asked for Colophon to be treated as potentially public-facing. The static audit (route-by-route) plus a live smoke test found real gaps: an unauthenticated provider-relay endpoint, an SSRF channel through the form's cover_url, two mutation routes that skipped CSRF verification, blocking I/O stalling the single-worker event loop, unbounded RAM/table growth an attacker could drive, a username-enumeration timing oracle, a cross-tenant room-name leak, an unhandled FK violation 500, and several missing hardening headers — plus dead config (`COLOPHON_SECRET_KEY` was read by nothing, yet README/compose documented it as a "cookie signing key") and dead code left from earlier milestones. Separately, the test suite had one deterministic failure in this environment (`test_seeding_twice_leaves_identical_counts`, `unable to open database file`).

## Decision

Shipped fixes, all verified by the 456-test suite plus a curl smoke pass against a real server. Access control: GET /book/lookup now requires `current_user` like every other /book route. SSRF: `fetch_provider_cover` resolves the URL's host against `ALLOWED_COVER_HOSTS` (covers.openlibrary.org, books.google.com, images.isbndb.com, subdomains included) and refuses everything else; `test_provider_cover_rejects_non_provider_hosts` pins the contract with metadata/loopback/attacker URLs. CSRF: both photo routes verify the token (add_photo reads the multipart form itself, so it calls `verify_csrf` explicitly), and both login and `verify_csrf` compare with `secrets.compare_digest`. Robustness: `login`, `book_lookup`, `create_book`, `update_book` are plain `def` so bcrypt/httpx block in FastAPI's threadpool instead of the single worker's event loop (T2); `add_photo` reads at most `MAX_UPLOAD_BYTES + 1`; `record_failure` prunes `login_attempts` rows older than the lockout window; a login against an unknown username verifies a dummy bcrypt hash so timing cannot enumerate users. Multi-user correctness: `_room_id_for_owner` rejects another owner's room_id, and `_parse_form` validates `primary_genre_notation` against the curated GENRES set (a junk value was an unhandled FK violation → 500). Hardening headers: `x-frame-options: DENY` on every response, `cache-control: private` on owner-scoped photos, `openapi_url=None` so /openapi.json no longer maps the API anonymously. Config truth: `COLOPHON_SECRET_KEY` and `DEV_FALLBACK_SECRET_KEY` are deleted from app/settings.py, docker-compose.yml and README — nothing ever read them (sessions are random DB tokens, not signed cookies), and the startup warning I had added for them was removed with them rather than left lying. The D11 banner check now also matches `demo`/`demo` via seed_data's DEMO_PASSWORD. Dead weight removed: `purge_expired_sessions`, `csrf_input`, `count_books`, `DEFAULT_USERNAME`, the unused `itsdangerous`/`python-dotenv` pins, and an empty template `{% if %}`. Root-caused suite flake: SQLite temp b-trees from the FTS reindex triggers spill to a temp file on long-lived connections mid-transaction and die as bare `unable to open database file` in restrictive environments; `app/db.py` and `tests/alembic_runner.py` now set `PRAGMA temp_store=MEMORY` (parity with the app engine). Negative guarantees: /healthz, /login and /static remain the only unauthenticated surface (by design); the dev-bypass CSRF skip is untouched and dev-only; no ORM was introduced; provider keys still never reach logs, export, or URLs.
## Alternatives considered

**Sign cookies with itsdangerous to make COLOPHON_SECRET_KEY real.** Lost: adds a mechanism nothing needs — session ids are already 256-bit random tokens validated against the DB; signing adds nothing but a dependency. **Refactor lookup/upload to httpx.AsyncClient.** Lost: a culture call — three similar blocking calls beat an async client rewrite; `def` conversion is zero new code and tests proved it transparent. **Make the settings page stop echoing provider API keys.** Deferred as a product decision: the key belongs to the same reader viewing their own authenticated page, and the alternative (write-only keys with a stored-hint) changes save semantics (blank = keep vs clear) and needs a clear-key UI. **Delete the demo user from `make serve` paths.** Deferred: demo/demo is the documented dev fixture (Makefile), and the banner now covers it; removing it is a workflow decision for the owner. **Fix the banner dismiss button vs D11 "non-hideable".** Deferred: it returns on the next page load, which arguably meets intent; removal is a UI call, not a security one. **Pagination/LIMIT on shelf and export queries.** Deferred: owner-scoped self-DoS only, dropdowns already capped at 500; a personal library will not hit it.
## Consequences

Bought: a server that survives being pointed at the internet's hostile edge cases — no unauthenticated relays, no SSRF, bounded tables and uploads, timing-equalized login, threadpool isolation for blocking work, and a test suite that is green on machines whose /tmp misbehaves. Cost: `COLOPHON_SECRET_KEY` disappears as a knob (deployments that set it are setting nothing — harmless but silent); `def` handlers mean FastAPI threads touch SQLite, which the per-request session pattern already made safe; provider cover hosts are now frozen into `ALLOWED_COVER_HOSTS`, so a new provider's image host requires a one-line addition there. Named coverage gaps: `add_photo` still runs Pillow on the event loop (bounded by the 10 MB cap and post-auth); expired sessions are purged only lazily; the settings page still echoes the reader's own API key into HTML.
